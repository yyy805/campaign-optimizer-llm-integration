# 项目回顾

## 背景

2026-08-13/14，对已完成的"大模型接入"工作按十阶段流程补全正式交付件：PRD → 史诗与故事 → 架构脊 → 测试设计 → 实施记录 → 代码审查 → QA/E2E → Sprint 状态 → 技术规范 → 回顾。每阶段经对抗式审查 + 用户审核门。

## 做得好（保持）

1. **测量→归因→最小修正**：Reviewer 校准循环（v6 6/8 → v9 零判断错误）每轮只回答一个问题、预算封顶、失败先诊断不盲重跑。
2. **自证监考**：变异/负例/伪造桩/零 provider 桩，让"门禁抓得住错"和"零消耗"都是被证明的事实。
3. **诚实作为资产**：开放项（O-6/O-7）、自报口径、未验项全部如实标注；审查抓到的自我夸大（587 口径、"已确认"措辞）当即修正。
4. **双维度自动放行门**（置信度×可逆性）与**混合 RAG 权威分割**，经受住对抗构造审查。
5. **交付件链互相对账**：PRD↔故事↔脊↔测试↔实施↔QA 六面一致，追溯矩阵逐行落地。

## 做得不好（改进）

1. **口径漂移复发两次**（587 vs 570；"已确认可行" vs 待验）——数字与状态进文档时必须带口径与根，摘要不裸奔。
2. **子代理不稳定**：代码审查子代理两次执行失败，回退亲审——关键审查要有降级预案。
3. **部署策略晚变更**：Docker 在老师确认后才退出主方案，文档留下"备选未验证"尾巴——外部决策应尽早进开放项并挂触发器。
4. **租期压力**：ECS 2026-09-12 到期，续费决策窗口（约 09-05）已挂触发器，需按时闭环。

## 教训固化

- 凡总结必带口径与证据根；待验项永不写成已验。
- 门禁一律 fail-closed；概率组件只提建议，代码持有裁决。
- 版本盖章：改一字 = 升版 + 冻结考卷复验。
- 每个 review 都过用户审核门；修订范围由用户裁决。
- 触发器闭环：缺口不靠记忆靠事件触发器（R5 转正、首跑、合并、续费）。

## 数字

十阶段全关闭；主交付件 9 份 + 审查报告 7 份；审查发现共 30 条全部闭环（PRD 两轮 10+8、脊 11、测试设计 7、代码 5（2 修 3 接受）、QA 2、规范 3）；代码修订 2 处入库（c3c1336）；阈值机器化入库（a9f1513）。
