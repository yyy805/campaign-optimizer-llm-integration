## 三分钟导读

**目标一句话**：给广告审核系统装一个"AI 解释员"——把"投放方案 + 本体审核"翻译成人话；红线是**只解释、不下结论，没批准的事必须说"还没批准"**。

**一张图看架构**：

```
用户 → Streamlit 演示网页 → 我们的后端（Python，所有安检在这里）
                                ├─ Triage 门卫：这问题该不该接？
                                ├─ Executor 写手：起草解释
                                ├─ Reviewer 质检员：审查草稿，挑违规
                                └─ 门禁代码：字段级校验，不过就安全回退
                              ↕ 只借"推理能力"
                           百炼 Qwen 大模型（不提供判断权威）

知识两条通道：
  主通道（权威）：本体发布包 → 按编号直取、版本锁定 → 可信上下文
  辅通道（阅览室）：百炼知识库 → 语义检索 → 只服务补充性问答
```

## 一、架构总览：三条线、四个角色、两条知识通道

**用户线**：网页 → 后端 → 回答。用户看到的永远是通过全部门禁的回答，或一句安全的"无法回答"。

**知识线**（最容易讲错的部分，务必分清）：
- **主通道是"按编号直取"**：本体团队发布规则包（带校验和），我们按审核钉死的编号取出对应规则原文，塞进模型的"可信上下文"。不经过任何搜索，因此不会漏、不会串、版本可锁。
- **辅通道是百炼知识库**：语义检索，只服务补充性问答。它的结果一律当"不可信数据"，**永远不参与裁决**。
- 类比：主通道像"档案室按编号调卷"，知识库像"阅览室随便翻"。定案依据只能来自调卷，不能来自随便翻。

**安全线**：模型每一步输出都过我们自己的代码门禁——格式不对拒收、引用越界拒收、篡改身份拒收、拿不准回退。原则叫 **fail-closed：保险丝宁可断电，不可起火**。

**四个角色**：门卫（Triage）决定接不接；写手（Executor）起草；质检员（Reviewer）挑违规；**真正拍板的是门禁代码，不是模型**——模型只提建议，代码做决定。

## 二、八步：做了什么 / 为什么 / 产出了什么

### 第 1 步 · 立契约（打地基）
**做了什么**：给模型输出定"填空模板"：请求、上下文、工作流输出、本体审核、最终方案各一份；写校验代码，缺字段/错类型立刻拒收。
**为什么**：模型说话是概率性的，系统要确定性。没有模板，后面所有测试都没有对错标准。
**产出**：
- 模板：`campaign_optimizer/schemas/`（5 份 JSON Schema）
- 校验代码：`campaign_optimizer/contracts/`（validation.py 等）
- 样例数据：`tests/fixtures/plan_a/`（一套完整的方案+审核演示件）
- 交接文档：`_bmad-output/planning-artifacts/l1-contract-freeze-handoff.md`
**验收**：契约测试组全绿；此后任何输出越框即拒。

### 第 2 步 · 连通性烟雾测试（通水通电）
**做了什么**：用最简单的一句话真实调用一次模型。
**为什么**：把"管道通不通"和"内容对不对"分开验证——否则出问题不知道是哪层的锅。
**产出**：连通脚本 `scripts/smoke_qwen.py`；记录四项（调用成功、请求 ID、延迟、token 数）。
**验收**：真实调用成功，密钥/区域/额度确认无误。

### 第 3 步 · 三角色分工（设立质检岗）
**做了什么**：Executor 写解释、Reviewer 审解释、Triage 判路由；给每个角色写提示词；加"预算账本"——每个案例最多调几次模型，超了自动停。
**为什么**：一个模型自说自话没人检查；预算账本防止失控烧钱。
**产出**：
- 代码族 `campaign_optimizer/llm/three_role_runner_v5–v13`（逐版继承，不毁旧版）
- 提示词 `prompts/`（executor_v4、reviewer_v6→v9、triage_v2）
- 角色配置 `agent_roles.v5–v15`（提示词哈希钉死：改一个字都必须升版复验）
**验收**：各版本离线测试累计数百项全绿。

### 第 4 步 · 与本体新版本对齐（换权威考纲）
**做了什么**：本体团队把核心规则 R5 改为"待人工审核"。我们把它的新发布包接入系统：版本锁（六个身份字段+校验和）、"待审核规则不得当证据"的 fail-closed 门禁、防篡改测试；在隔离分支合并验证后才进主线。
**为什么**：判断依据必须来自权威来源，不能用自己编的 demo；"没批准就不当证据"是产品红线。
**产出**：
- 版本锁 `llm/release_pin.py`、发布清单 `ontology/publication_manifest.json`、冻结发布包 `.ontology_bundles/`
- 14 项收敛门禁测试 `tests/test_llm_convergence_integration.py`（任一身份字段被篡改，在调模型前就失败）
- 合并提交 `38fcc6d`
**验收**：14 项门禁 + 全量回归全绿；主分支零污染。

### 第 5 步 · Reviewer 业务验收（核心故事，四轮考试）
**做了什么**：写"冻结考卷"（8 道题、答案预冻结）考 Reviewer；按"测量→归因→最小修正"循环迭代提示词 v7→v8→v9。
**为什么这么多轮**：单考一次分不清"真会"还是"运气好"。分数振荡（6→5→6→8）不是返工，是测量仪器变精确：第一轮发现两个缺口；第二轮修好但过度审查；第三轮发现是"边界噪声"（同答案时对时错）；第四轮用"一个对的例子+一个错的例子"校准，连考两轮 8/8 加补考，零错误。
**产出**：
- 冻结考卷 `tests/fixtures/llm_eval/reviewer_judgment_v1/`（8 案例 + 验证器 + 守护测试）
- 评测脚本 `scripts/run_reviewer_judgment_eval_v14.py`（含安全诊断字段：只看模型引用了哪条规则，不泄露内容）
- v9 提示词 + 钉死配置 `agent_roles.v15.json`
**验收**：真实调用两轮 8/8 + 补考 1/1，零判断错误；每轮预算封顶（≤16 次）。

### 第 6 步 · 路由安全（门卫制度）
**做了什么**：硬路由（复合问题/恶意提问直接礼貌拒答）+ Triage 弃权机制 + 意图白名单。
**为什么**：门禁的意义不在答得多，在于不该答的一个不放。"不知道"永远好过"胡说"。
**产出**：硬路由 `llm/intent_policy.py`；50 题路由安全数据集 `tests/fixtures/llm_eval/v1/routing-safety.json`。
**验收**：真实测试三层全 fail-closed（复合问句 0 调用拒答；拿不准弃权；白名单外回退）。

### 第 7 步 · 轻量知识库（建阅览室，分清主次）
**做了什么**：把 7 张规则卡**原样**（不重写一个字）导出为知识库文档，上传百炼；用 12 道冻结检索题验收。
**为什么**：规则将来会增多，不能全塞对话；但检索可能漏、可能串，所以只做补充通道（架构不变式见第一节）。
**产出**：
- 导出脚本 `scripts/export_knowledge_base_v1.py` + 快照 `kb_export/v1/`（7 文档 + 版本清单）
- 检索题卷 `tests/fixtures/kb_retrieval_v1/questions.json`
- 百炼知识库 `eeirxr7djz`；发布台账 `docs/knowledge-base-publications.md`
**验收**：5 硬门全过——"查 R5 只返回 R5"、R5 带"待人工审核"标记、R7 带"已退役"、恶意提问无结果。关键发现：默认阈值 0.20 会捞回噪声，调到 **0.60** 才过——该阈值已写入台账，成为发布配置的一部分。

### 第 8 步 · 交付（让别人能接手）
**做了什么**：演示网页、ECS 直接部署配方（与老师确认不用 Docker）、给本体团队的交接文档、ECS 开通。
**为什么**：只有作者能跑的系统不是交付品。
**产出**：`app.py`（Streamlit，dry-run 默认）、ECS 部署配方（`Dockerfile` 保留为备选交付物）、`docs/handoff-ontology-team-2026-08-06.md`（架构红线+部署清单+R5 转正重发布流程）、上海 ECS 实例（标识符见内部台账）。
**验收**：网页侧边栏显示版本锁与 v9 提示词；dry-run 零调用；全部推送 GitHub。

## 四、老师可能追问的问题

**Q：为什么测了这么多轮，是不是效率低？**
A：每轮问不同的问题（有没有能力→规则对不对→是不是噪声→校准有效吗）。每轮预算封顶、只回答一个问题、绝不盲重跑。真正的浪费是"跑一次看看"然后凭感觉改。

**Q：为什么不用大模型平台现成的流程？**
A：平台是黑盒。我们的安全门禁（fail-closed、版本锁、字段级校验）必须放在自己代码里才能完全控制。我们只借平台的"推理能力"，编排和安检自己做。

**Q：怎么测试脚本和提示词是否完成？**
A：三层。① 离线练习（587 项，零花费）：除了正常案例，还"故意做错"（篡改字段、伪造身份、注入提问）证明监考抓得住；并装"假开关"证明离线模式真不联网。② 彩排（dry-run）：每个脚本默认完整走流程但零真实调用，只报计划（题数、预算、模型），结构对了才上真场。③ 正式考试：真实调用走冻结考卷+事先声明的验收标准，每轮封顶。提示词用"版本盖章"：文本哈希钉死，改一个字=升版重考；离线考"规则写没写进纸面"，真实考"活干得好不好"（连续两轮 8/8）。管道安全（代码门禁）与判断质量（提示词）分开考。

**Q：烧了多少钱？**
A：全部真实调用约 45 次、15 万 tokens，人民币个位数。离线 587 项测试不花钱。

**Q：概念卡（术语定义）为什么没进知识库？**
A：它们现在的角色是"结构权威"——代码按编号直取做校验，不需要检索；且与规则卡共享词汇，放进去会让"查 R5"捞回概念片段，验收第一天就变浑浊。放入时点已预定：开放"术语解释"意图时，走现成流程（导出→上传→带 0.60→加题验收→记账）。知识库是阅览室，不是档案室。

**Q：还有什么没做完/不完美？**
A：三件，都如实记录——① 小模型 Triage 对某些问句误路由，但所有失败安全兜底，网页主路径不经过它；② R5 等本体团队人工审核转正，转正后有现成重发布流程；③ 上云由本体团队执行，交接文档已写好。

## 五、成果数字

离线测试 587 项全绿；Reviewer 验收零判断错误；检索 5 硬门全过；路由三层真实验证全 fail-closed；约 20 个提交全部推送；知识库发布与本体版本一一记账。
