# 项目进度汇报：本体 × 大模型的广告决策审查 Demo

> 截至 2026-08-06。面向进度汇报编写，技术名词在文末有一句话解释。

## 一句话总览

我们在做一个**广告决策审查助手**：归因分析（MTA）模块给出"预算该怎么调"的建议后，系统用一套形式化的业务规则库（本体）审查这个建议，大模型把审查结果用人话解释给用户。全链条已跑通、代码已全部推送，下一步是部署上云。

**核心设计原则：规则负责判断，大模型负责解释，一切按版本可追溯。**

## 整体架构（简图）

```text
MTA / Agent 分析结果
        ↓
审查引擎：按本体规则（R1–R7）与安全护栏（G1–G2）独立匹配
        ↓
三类判定：MATCH（一致）/ CONFLICT（冲突）/ NO_COVERAGE（无覆盖）
        ↓
三角色大模型：Triage 路由 → Executor 生成建议解释 → Reviewer 合规审查
        ↓
Streamlit 网页 Demo（默认 dry-run，不花一分钱真实调用）

旁路（只补充、不裁决）：百炼知识库检索
治理闭环：用户反馈 → 治理任务 → 人工审批 → 新版本发布（反馈绝不自动改规则）
```

## 里程碑：每一步做了什么、为什么这么做

### 1. 把"业务常识"写成机器可读的规则库（本体 v1.1-demo）

- **做了什么**：把广告场景的指标概念（ROAS、花费等）、7 条决策规则 R1–R7、2 条安全护栏 G1/G2、数据格式约束，整理成带版本号、可自动校验的规则包。
- **为什么**：业务判断依据必须"写下来、能验证"。否则大模型自由发挥，错了也无法追溯。这是整个系统可信度的地基。

### 2. 审查引擎与可追溯的存储

- **做了什么**：实现审查引擎（规则匹配、多规则冲突处理、三类判定）；每次审查、每条用户反馈都完整入库；数据库结构用迁移工具（Alembic）管理，写操作带原子事务和并发保护。
- **为什么**：审查结果要能回查、能审计。Demo 出了问题，要能回答"当时用的是哪个版本的规则、依据是什么、谁反馈了什么"。

### 3. 版本钉扎与发布身份（全项目的"合同"）

- **做了什么**：每次规则包发布生成一份"发布清单"：每个文件的哈希值 + 各层版本号，并冻结成快照随代码分发；任何消费方使用前先逐条校验哈希，对不上就拒绝运行（fail-closed）。
- **为什么**：本体、大模型、API 三条线并行开发，必须保证大家用的是**同一版规则**。哈希校验让"有没有人偷偷漂移"一键可查——这次整合核查就是靠它发现并定位了工作区漂移。

### 4. 大模型接入：判断与解释分离

- **做了什么**：大模型**不参与裁决**。权威规则上下文由钉扎版本确定性投影提供；LLM 只生成解释与补充。三角色分工：Triage 决定问题走哪条路，Executor 生成建议与解释，Reviewer 做合规审查（Function Calling 结构化输出）。
- **为什么**：控制幻觉。大模型擅长表达、不擅长稳定守规则；把"判断权"给规则、"表达权"给模型，是可靠性边界。

### 5. Reviewer 提示词迭代 + 冻结测评验收

- **做了什么**：建了一套冻结测评集（8 个典型病例，含合规、违规、注入攻击、因果夸大等），审查提示词从 v6 迭代到 v9；每轮"测量 → 归因 → 最小修正"。最终连续两轮全对 + 补证，**零判断错误**，验收关闭。期间还诊断出"边界噪声"（模型坐在判定边界上偶尔翻转），用校准示例钉死。
- **为什么**：改提示词最怕"修一个坏三个"。冻结测评集 + 硬门槛保证每一轮迭代是净进步，而不是运气。

### 6. 路由安全验证

- **做了什么**：真实调用验证：超出范围的复合问句被硬路由拒绝（0 次模型调用），单意图问句的 Triage 在不确定时弃权并安全兜底。
- **为什么**：fail-closed——拿不准就不答、不执行。这是面向用户的安全底线。

### 7. 轻量 RAG 与知识库验收

- **做了什么**：把规则库导出为知识库快照（7 篇文档）发布到百炼知识库（编号 `eeirxr7djz`），相似度阈值设为 0.60，用 12 条冻结检索题验收（关键 5 条真实跑通）："查 R5 只返回 R5"、停用规则显示停用、域外探针返回"未检索到"而非编造。
- **为什么**：混合 RAG 不变式——权威通道仍是确定性投影，知识库**只是补充检索**，检索结果被视为不可信数据、永不参与裁决。0.60 阈值是发布配置的一部分（默认 0.20 会让污染与探针硬门失败），已记入版本台账，任何重发布必须携带。

### 8. Demo UI 与镜像方案

- **做了什么**：Streamlit 网页 Demo（默认 dry-run、零真实调用；真实调用需显式环境变量）；Dockerfile 含冻结依赖与规则快照，镜像内 release-pin 自检。
- **为什么**：老师和大家能直接看到、玩到；镜像保证"本地测什么、云上跑什么"，环境不一致的坑提前消掉。

### 9. 三线整合、交接与上云准备

- **做了什么**：大模型侧全部完成并推送（`main = 2724f02`），交接文档列明架构不变式、交付物清单、ECS 部署四步；知识库台账行已与本体发布校验和锁定，待联合验收。本体侧 Review API（含反馈、治理任务状态机）测试全绿、Docker 配置就绪。
- **为什么**：两条线各自建设、以**版本身份**为锚点汇合，避免"演示前夜集成地狱"。

## 附：关键术语一句话解释

- **本体（Ontology）**：机器可读、可校验的业务规则知识库（概念 + 规则 + 护栏 + 格式约束）。
- **release-pin（发布钉扎）**：所有消费方锁定同一份带哈希的发布快照，校验不过就拒绝运行。
- **fail-closed**：不确定时宁可拒绝/不执行，也不冒险给出答案。
- **冻结测评集**：固定不变的验收用例集，提示词/规则任何改动都必须通过它，防回归。
- **混合 RAG**：权威规则走确定性投影，知识库只做补充检索且不参与裁决。
- **治理边界**：用户反馈 ≠ 自动修改规则；正式修改必须新版本 + 人工审批 + 记录回滚点。
