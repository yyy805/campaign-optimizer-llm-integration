## 第 1 章 📋 线 1：回溯式正式化流水线

### 1.1 为什么要做这条流水线

代码和系统**已经做出来了**，但"做出来"和"能向老师证明它做得对"是两件事。缺的是：需求文档（为什么做这些功能）、架构文档（为什么这样设计）、测试设计（为什么这些测试够了）、追溯矩阵（每个需求是否有测试接）。回溯式正式化 = **对着已完成的现实，补齐全套工程证据链**。它不是重写系统，是把"我们当时为什么这么做"从脑子里和聊天记录里，搬进可审查的文档。

### 1.2 为什么是这个顺序（以及我们犯过的错）

标准顺序：**需求 → 架构 → 故事**。我们最初按用户直觉排成"需求 → 故事 → 架构"，在故事拆解技能的预检里发现架构是故事的必需输入（故事要引用架构决策），于是**调回标准顺序**。这个插曲值得讲给老师：方法论的顺序不是教条，而是依赖关系——故事的验收标准要引用架构的不变式，架构不存在时故事就是悬空的。

### 1.3 为什么每步之后要对抗审查 + 人工决断

AI 生成的文档最大的风险是"自说自话"——自己写自己点头。我们的治理约定：**每步产出 → 对抗审查（专门挑刺的审查）→ 把问题逐条解释给你（是什么/为什么要修/怎么修/不修会怎样）→ 你逐项决定修不修**。八轮 review 共产出 60+ 条发现，每条都有你的决断记录（审计日志 memlog 可查）。这意味着文档里的每个数字、每条映射，都被"另一个挑刺视角 + 人类负责人"双重过过。

### 1.5 为什么流水线结果可信（证据链）

1. **每个声明带证据指针**：实现记录里"recorded"的每条都指向具体测试文件或本会话实测输出（如 bundle 逐条验真 OK、API 76 passed）。
2. **诚实的三态标签**：不假装全做完。pending-merge = 实现在集成分支、等合并门；pending-exec = 真实剩余工作。老师能看到"哪里还没做"，这比全绿更可信。
3. **追溯矩阵无孤儿**：31 条需求每条有测试接，29 个测试每个有需求归属；交叉核对过。
4. **决断可审计**：八轮 review 的每条发现与你的决断，都记在 memlog 与文档注记里，可回溯"谁在什么时候决定了什么"。

### 1.6 老师追问预备（线 1）

- **Q：为什么用 AI 走流程还可信？** A：AI 只起草；每步有对抗审查挑刺 + 人工逐项决断 + 证据指针 + 部分声明真实跑过验证（测试输出/双跑）。可信度来自"链条"，不来自任何一个环节。
- **Q：为什么就绪门是"条件性通过"而不是"通过"？** A：诚实口径。条件 = 合并门证据到位等，全部明确列出并有负责人/时线；条件清零即转 PASS。
- **Q：追溯矩阵自己报 31/31，怎么知道没漏？** A：矩阵由"需求文档 FR 列表"与"测试设计 T 列表"双向比对生成；review⑦ 还专门查出 5 个缺口并补登记（T-25..T-29）——查缺能力本身被验证过。

## 第 2 章 🏗️ 线 2：PG 换库演练

### 2.1 为什么要换库、为什么"验证过地转"

老师提议把演示的运行库从 SQLite（单机文件库）换成阿里云 PostgreSQL（云数据库），更接近生产形态。**直接换的风险**：方言差异（两库对同一条 SQL 的规矩不同）、数据丢失、行为分叉。所以原则是"**验证过地转**"：先在"排练厅"（独立测试库 mta_data_test）把服务在 PG 上的全套动作演一遍，再动真库；真库先放空表（摆桌子），搬数据前停写+对账，切换前双跑，**双跑不过不切换**，切换后旧库留两周兜底。

### 2.2 七步各自的作用与"为什么不能省"

| 步 | 作用 | 省了会怎样 |
|---|---|---|
| 0 凭据安全存放 | 连接串进 .env.pg（git 自动忽略），不进聊天/截图/提交 | 凭据泄露只能轮换，且进 git 历史就永远在 |
| 1 探路 | SELECT 1 + 临时表读写，验证网络/白名单/SSL/权限 | 80% 的坑（白名单/SSL/权限）会在后面更贵的步骤才暴露 |
| 2 体检 | 在**测试库**上真启动服务，跑 Hannah 预置验收题（建表/写入/幂等/防篡改/重启读回/清理） | 服务在 PG 上的行为差异会直接发生在真库 |
| 3 建表 | 真库摆 13 张空表（先 5 后 8） | 先 5 后 8 是因为 8 张里有外键"认 5 张里的表当爹"，爹不在建不出来 |
| 4 空搬 | 空源库跑搬迁脚本，验证"内省→拓扑序→INSERT→对账"机制 | 机制缺陷会在真数据搬迁时才暴露，代价大 |
| 5 双跑（灵魂） | 同一标准案子在 SQLite 与 PG 各跑一遍，比对审查编号/总判定/完整返回/四张表行哈希 | 行数对账只证明"搬过去了"，双跑才证明"同一输入同一结论" |
| 6-7 切换+台账 | 配置指向 PG + 冒烟三件套 + 旧库留两周 + 台账记一行 | 无回滚兜底、下一个值班人不知道主库是谁 |

### 2.3 本周真实踩到的 10 个坑，以及它们为什么反而证明可靠

| 坑 | 暴露于 | 证明/收获 |
|---|---|---|
| PowerShell 用 set 记环境变量不生效 | 步 1 | 操作侧方言差异，已进终稿排查表 |
| 密码含 @ 必须 %40 转义 | 步 1 | URL 解析规则，已进排查表 |
| 普通账号无 CREATEDB | 步 2 前 | RDS 账号分层是安全设计；经控制台授权解决 |
| alembic 老解析器把 % 当占位符 | 步 3 | 密码改走 PGPASSWORD 环境变量（更安全） |
| SQLite/PG 方言口味相反（batch vs 逐条） | 步 3 | 迁移改"按方言分菜"，两库都过；此修正将随合并门并入 |
| 连接串缺 connect_timeout 会崩 | 步 2 | 代码对缺省空串转数字的缺陷暴露；补参数解决 |
| alembic_version 台账不该搬 | 步 4 | 搬迁脚本加排除清单 |
| 粘贴连行（--yesuv） | 步 4 | 操作侧坑，进排查表 |
| 体检初败于 connect_timeout（被服务吞错） | 步 2 | 写了"探针脚本"让被吞的错误现形——**可观测性投资的回报** |
| 外键依赖拦拆表（PG 严格） | 步 3 | 同上"方言分菜" |

**为什么踩坑不减分反而加分**：每个坑都在"成本最低的步骤"暴露并修复（探路/体检/空搬），没有一个带病进入双跑；最终双跑 16 项 PASS 是**端到端**证据——它站在所有修复的肩膀上。

### 2.4 为什么双跑 PASS 是强证据

- 比对的是**确定性输出**：审查编号 = 输入种子的哈希，总判定与完整返回逐位比对，四张持久化表行哈希比对。任何 schema/约束/JSON 往返差异都会让哈希分叉。
- 唯一排除项是墙钟时间戳（两次跑时间必然不同）——排除合理且公开声明。
- 幂等与重审链也在比对内（同键重放逐位一致、revision=1 父链一致）。

### 2.5 回滚路径在哪

- 双跑不过 → 不切换（硬门）。
- 切换后异常 → 配置指回 SQLite（旧库留两周，改名存档）。
- 任何一步失败 → 该步之前的状态都保持可用（空表可删、测试库可弃、凭据可轮换）。

### 2.6 老师追问预备（线 2）

- **Q：为什么用空库做搬迁演练？** A：真实数据尚不存在（服务未正式运行，历史全是 dry-run/临时库测试）。空搬验证机制，双跑验证行为，两者拼起来才是完整证据；真数据将在切换后直接生于 PG。
- **Q：体检题为什么合理？** A：八步对应换库最怕的八件事（建表失败/写不进/重复写/篡改/重启丢数据/污染真库…），且三重安全锁（无环境变量即跳过、库名必须 _test 结尾、人工确认开关）保证验收题永远碰不到真库。
- **Q：为什么相信 PG 上的判定和 SQLite 一样？** A：双跑 16 项 PASS；且引擎本身零模型调用、纯确定性代码，差异只能来自存储层——而行哈希比对正是针对存储层。
